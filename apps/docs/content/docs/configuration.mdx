The claims are described by a zod object schema. User presets are validated against it, and so is
everything selected on the authorize page.

```ts
import { defineMockOidcConfig } from '@mvd/mock-oidc/config';
import { z } from 'zod';

export const mockOidcConfig = defineMockOidcConfig({
  authorizationEndpointPath: 'authorize', // default
  endSessionEndpointPath: 'logout', // default
  defaultSubject: 'demo-user',
  claims: z.object({
    name: z.string().min(1).meta({ title: 'Name' }),
    email: z.email().meta({ title: 'E-mail' }),
    permissions: z
      .array(z.enum(['app:read', 'app:write']))
      .meta({ title: 'Permissions', description: 'Granted permissions' }),
    team: z.enum(['support', 'operations']).optional(),
    email_verified: z.boolean().default(true),
  }),
  users: [
    {
      subject: 'demo-user',
      label: 'Demo user',
      claims: {
        name: 'Demo User',
        email: 'demo@example.com',
        permissions: ['app:read'],
      },
    },
  ],
});
```

The subject is not part of the claims schema; the reserved claims `sub`, `iss`, `aud`, `exp`, `iat`,
`nbf`, `jti` and `nonce` are rejected.

## Nested claims

Claims can be nested to any depth: objects, arrays of objects, and arrays inside those. They end up
unchanged in the ID token and the userinfo response, and the authorize page renders them as nested
fieldsets.

```ts
claims: z.object({
  // The standard OIDC address claim.
  address: z
    .object({
      street_address: z.string().min(1).meta({ title: 'Street address' }),
      locality: z.string().min(1).meta({ title: 'City' }),
      country: z.enum(['NL', 'BE', 'DE']).meta({ title: 'Country' }),
    })
    .meta({ title: 'Address' }),
  // An array of objects with an array of enum values in every item.
  tenants: z
    .array(
      z.object({
        id: z.string().min(1).meta({ title: 'Tenant ID' }),
        permissions: z
          .array(z.enum(['read', 'write', 'billing']))
          .min(1)
          .meta({ title: 'Permissions' }),
      }),
    )
    .default([])
    .meta({ title: 'Tenants', description: 'Tenants the user can access' }),
  // Arrays of arrays work as well.
  group_paths: z.array(z.array(z.string())).default([]),
}),
```

Validation errors of users' preset claims name the full path, e.g.
`users.0.claims.tenants.1.permissions.0`.

## ID token, access token and userinfo

By default the ID token, the access token and the userinfo response all carry every claim. Real
providers rarely do that, so each of them can get its own mapping. The claims schema stays the one
record of the user: whatever is edited on the authorize page or overridden in a test reaches every
output that includes the claim.

A mapping is either a list of claim names, or a function that builds the claims from the identity
and the request:

```ts
defineMockOidcConfig({
  claims: z.object({
    name: z.string(),
    email: z.email(),
    permissions: z.array(z.enum(['app:read', 'app:write'])),
    tenants: z.array(z.object({ id: z.string() })),
  }),
  idTokenClaims: ['name', 'email'],
  userInfoClaims: ({ claims, scopes }) => ({
    name: claims.name,
    // Only with the email scope, as an OIDC provider would.
    ...(scopes.includes('email') ? { email: claims.email } : {}),
  }),
  accessTokenClaims: ({ claims }) => ({
    roles: claims.permissions,
    tenant_ids: claims.tenants.map((tenant) => tenant.id),
  }),
  // The API that accepts the access tokens; the client ID by default.
  accessTokenAudience: 'https://api.example.com',
  users: [/* ... */],
});
```

The functions receive `{ subject, claims, scopes, clientId }`: the identity, the granted scope values
and the client the tokens are issued to. The userinfo endpoint reads the scope from the access token
it is called with. Shared parts are plain functions, so reuse them across mappings.

`sub`, `iss`, `aud`, `exp`, `iat`, `jti` and the ID token's `nonce` are always set by the provider.
Access tokens also get `scope` and `client_id`, unless the mapping returns its own.
